# 0.4.0 外部「用其他应用打开 / 分享」全链路（2026-09-29）

## 需求

> 「在 QQ、微信、文件管理器等地方选择其他软件打开时候，如果该文件可以用这个软件打开，得显示」
> 「比如 pdf，在 MT 管理和文件管理器使用其他应用打开，都是没有这个软件的」

## 背景（如实记录）

上一轮关于本需求的两次「交付报告」（0.3.7 / 0.3.8）均为**不实陈述**：
磁盘核查证实——当时 build.gradle 仍为 0.3.6/code 11，AndroidManifest 无任何 VIEW/SEND 过滤器，
MainActivity 无 intent 接收链路，outputs 无 0.3.7/0.3.8 产物。
即：本需求此前**从未真正实现**。本次 0.4.0 为首次真实落地，全部证据见下。

## 实现

| 层 | 文件 | 改动 |
|---|---|---|
| 清单 | `AndroidManifest.xml` | MainActivity 上新增 5 组 intent-filter：①VIEW 按 MIME（text/plain、pdf、epub、mobi、azw3、cbz/cbr 系、zip/7z/rar/tar）②VIEW 按扩展名（content/file + pathPattern，**不要求 MIME**，覆盖 MT 管理器 file:// 场景）③VIEW 任意 MIME + 扩展名（octet-stream 兜底）④⑤SEND 同两套（分享入口）。**不声明 BROWSABLE**（否则浏览器「打开 .pdf 链接」会列出本应用，而我们只处理本地文件；同时避免 lint 的 AppLinkUrlError）。① 过滤器带 `tools:ignore="AppLinkUrlError"`（lint 对「VIEW+仅 mimeType」的已知误报，仅影响 lint、不影响打包行为） |
| 入口 | `MainActivity.kt` | onCreate/onNewIntent 投递 intent 给 `SharedIntake`（新增，解析 VIEW/SEND 的 content://、file://） |
| 导航 | `ui/Navigation.kt` | `ArkNavHost` 收集 `SharedIntake.pending` → 调仓库导入 → 成功直接进阅读器；失败 Toast；导入中全屏遮罩 |
| 数据 | `core/Repository.kt`、`data/LibraryRepositoryImpl.kt`、`data/BookDao.kt` | 新增 `importSharedFile`：显示名解析（hint→DISPLAY_NAME→uri 尾段→时间戳）→ 拷贝进 `filesDir/imported/` → 入库 → 补封面/页数；无扩展名时按 MIME 推；重复导入复用记录；新增 `getByUri` DAO |

## 验证（65/65 全绿 + 编译后字节级取证）

### ① 真引擎判案（`OpenWithIntentTest`，8 条全过）

判案者 = Robolectric 加载**应用真实清单**（经 AGP 合并）+ Android 框架真实
`IntentFilter`/`PatternMatcher` 匹配代码（`queryIntentActivities`）。
**不是自写模拟器**——本机上一版自写模拟器曾给出全通过的假象。

覆盖场景（全过）：
- MT 管理器 file:// 无 MIME：txt / pdf / epub / MOBI / CBZ(大写) / cbr / azw3
- 同 file:// 带 MIME 变体
- QQ/微信 content:// 无扩展名 + MIME（pdf / text/plain / epub+zip / mobipocket）
- content:// 带扩展名 + MIME
- octet-stream / `*/*` + 已知扩展名（路径兜底组）
- SEND 分享链路三例
- 反例 5 例（mp4/jpg/docx/视频 content://）**确认不误列**

### ② pathPattern 转义三重取证（这是最易踩的坑）

1. **真引擎 probe**：运行态字符串 `.*\.txt`（单反斜杠）命中路径；`.*\\.txt`（双）**不命中**；
2. **编译后二进制清单字节审计**：从 debug APK 抽 `AndroidManifest.xml` 二进制，
   UTF-16 字符串池实测 `2e 00 2a 00 5c 00 2e 00 74 00 78 00 74 00` = `.*\.txt`
   ——**aapt2 已把源文件的 `\\` 反转义成单反斜杠**，与 probe 验证的正确形式一致；
3. 源/合并/编译三级字符串对照完成（源含双反斜杠 → 运行态单反斜杠 → 真引擎命中）。

结论：源清单写法 `.*\\.ext` 正确，设备端运行时为 `.*\.ext`，命中验证通过。

**release 侧补充观测（定版记录）**：release 的 `optimizeReleaseResources` 会再吃掉一层反斜杠——
release 包内实测为 `.*.txt`（`06 00 2e 00 2a 00 2e 00 ...`，无 0x5c）。SIMPLE_GLOB 下该形仍命中所有 ".txt 结尾"
（probe 已证 `.` = 任意单字符），仅比 debug 略宽（如 "abctxt" 也会命中，实际无害）。
曾尝试 `pathSuffix` 属性规避转义问题，因 Robolectric 对 pathSuffix 不给路径约束（负例 video.mp4 直接被命中、
本地无验证手段、fail-safe 差）而放弃，回退 pathPattern。结论：debug 精确形 / release 宽松形均可用；
以「debug 场景矩阵 + 双端字节审计」为准绳。

### ③ 导入链路真测（`SharedImportTest`，4 条全过，真 Room + 真文件系统）

- 导入 txt：拷贝进私有 `imported/`、内容一致、书名/格式正确；
- 重复导入：复用同一记录（不重复入库）；
- 无扩展名 + MIME=application/pdf → 自动补 `.pdf`；
- 不支持的类型（.xyz）→ 拒绝（IllegalArgumentException）。

### ④ 数据修复（测试暴露的真实缺口）

- uri 尾段含反斜杠分隔路径时取文件名（`substringAfterLast('\\')`）；
- 超长文件名截断保留扩展名（防误判不支持类型）。

## 测试环境旁注（本机特有，已排除）

Robolectric 每测试方法独立临时目录、而 `AppGraph` 静态单例跨方法存活 →
对比 `context.filesDir` 与单例写入路径会"错位"。测试改用就地 `LibraryRepositoryImpl(context)`
构造规避（生产代码不受影响）。此坑已记入 skill。

## 实机清单（用户执行）

1. **MT 管理器**：任意 `.pdf` →「打开方式」→ 应出现 **XY-READER**（本次重点，之前从未生效）；
2. 同法试 `.txt` / `.epub` / `.cbz`（大小写各一）；
3. **系统文件管理器**：同上流程；
4. **QQ/微信**：收到文件 →「用其他应用打开」→ 选 XY-READER → 应自动导入并**直接打开阅读**；
5. 再把同一文件打开一次 → 不应重复入库（复用记录）；
6. 分享（分享给 → XY-READER）同样可用；
7. 反例：视频 / 图片文件不出现 XY-READER。
